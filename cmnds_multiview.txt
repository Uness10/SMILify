# =============================================================================
# A. WHY 25 EPOCHS AND 2 NODES  (the answer to your two notices)
# =============================================================================
#
# A1. EPOCH COUNT — halve it, yes, and there is a second reason to.
#
# The single-view arms all finished: sweep.csv shows checkpoint_epoch 435 for
# every lambda (386 + 50 = 436, last periodic checkpoint at 435), at ~10-11 h on
# 1 node x 4 H100 = ~13 min/epoch. And the curve was already decided long before
# the end: violations collapse monotonically with lambda while MPJPE moves by
# <0.1 mm. Nothing in the last 25 epochs changed the ranking.
#
# The second reason is specific to the multi-view config and matters more:
#   multiview_SMILySTICKS_3D_ViT_Large_AUG_FIXED.json has curriculum_stages at
#   epochs 300 and 400 (joint_angle_regularization 5e-7 -> 2e-7,
#   limb_scale_regularization 5e-5 -> 1e-5). If the multi-view reference sits at
#   epoch ~354 (the number the study README uses for its multi-view dry run),
#   then:
#       +50 epochs -> 404   CROSSES the 400 boundary; every arm changes loss
#                           weighting 46 epochs in, mid-window
#       +25 epochs -> 379   stays entirely inside stage [300, 400)
#   The crossing is identical across arms, so lambda-vs-lambda stays clean
#   either way — but +25 also keeps reference-vs-lambda free of it. Confirm the
#   actual resume epoch in step 1 and re-check this arithmetic against it.
#
# The LR is not a problem here, unlike single-view: multi-view's lr_schedule is
# {0: 1e-4, 120: 5e-5, 200: 1e-5}, so any resume past epoch 200 sits on a flat
# 1e-5 for the whole window. No LR_FLAT needed. The [patch] lines in step 3 will
# say "lr constant at 1e-05" — if they instead print a WARNING, stop and set
# LR_FLAT to the value it suggests.
#
# COST OF 25: the multi-view arms are then NOT epoch-matched to the single-view
# arms. State that in the report — compare lambdas within a modality, and treat
# any single-view-vs-multi-view delta as qualitative.
#
#
# A2. THE WALL — the levers, in the order worth pulling.
#
#   1. --nodes=2  (8 ranks/arm, 32 H100 for the sweep). Roughly halves the wall
#      clock. Costs a longer queue wait and doubles the effective batch unless
#      you pass BATCH_SIZE — hence BATCH_SIZE=4 below (config is batch_size 8
#      per rank x gradient_accumulation_steps 2; 8 ranks x 4 x 2 = 64, the same
#      effective batch as 4 ranks x 8 x 2).
#
#   2. Ask for LESS wall time. 24 h is the account cap, and asking for the cap
#      makes you nearly unbackfillable. With 25 epochs on 2 nodes you should be
#      well inside 12 h; --time=12:00:00 starts materially sooner. Only raise it
#      if step 5's measured per-epoch time says you need to.
#
#   3. Submit to BOTH GPU partitions: --partition=c23g,c25g. Both are 4x hopper
#      per node (c23g: 50 nodes/200 GPUs, c25g: 29 nodes/116 GPUs) and both have
#      >=96 CPUs/node, so --cpus-per-task=96 is satisfiable on either. Slurm
#      takes whichever frees first. This is free and you should always do it.
#
#   4. If it still will not fit: do NOT lower dataset_fraction — it is already
#      0.2 in the multi-view config, and dropping it further makes the
#      violation rates noisier, which is the number the whole study rests on.
#      Chain instead. save_checkpoint_every is patched to 2, so a wall kill
#      costs at most 2 epochs, and both the eval array (--dependency=afterany)
#      and run_prior_study.sh fall back to the newest periodic checkpoint.
#
#   NOT useful here, despite appearances:
#     * `devel` / `devel_low` (MaxTime 1 h) are CPU-only nodes — n23m0123 and
#       r23m0124. There is no fast GPU debug queue on this cluster; the login
#       node dry run in step 4 is the substitute.
#     * the `_low` partitions are the same hardware at PriorityTier 10-70
#       instead of 1000. They only make sense if you want to stop consuming
#       fair-share and do not care when the job lands.
#
#   The real protection is not a partition trick: it is measuring the first
#   epoch (step 5) and reacting within the first hour, while a scancel is cheap.
# =============================================================================

# -----------------------------------------------------------------------------

print(f"embedded config keys: {sorted(cfg)[:12]}")

# -----------------------------------------------------------------------------
# 7. QUALITATIVE RENDERS — run_multiview_inference.py, the direct counterpart
#    to the run_singleview_inference.py you used for the single-view arms
# -----------------------------------------------------------------------------
# (run_prior_study_render.sbatch is single-view-only and irrelevant here — you
# did not use it for the single-view renders either.)
#
# The two entry points are NOT flag-compatible. What changes:
#
#   singleview                          multiview
#   ----------------------------------  ----------------------------------------
#   -v / --input_video <clip.mp4>       --dataset <the HDF5>      (REQUIRED)
#   -o / --output_folder <dir>          (none — writes into the CWD)
#   --max_frames N                      --max_frames N  = length of EACH subclip
#   (pick clips by hand)                --generate_num_subclips K
#   --camera_smoothing W                --smoothing_window W
#   --crop_mode / --video_export_mode   (no equivalent)
#   (smal file taken from the ckpt)     --smal_file <path>        (overridable)
#   --save_frames                       (always writes per-frame PNG + params)
#   n/a                                 --view_indices 0,4,11
#   n/a                                 --disable_translation     <-- SEE BELOW
#   n/a                                 --render_resolution, --num_gpus
#
# THREE THINGS THAT WILL BITE:
#
#  1. --disable_translation DEFAULTS TO TRUE. It is a BooleanOptionalAction with
#     default=True, so plain invocation renders with per-part translation
#     (betas_trans) switched OFF. The multi-view config trains with
#     scale_trans_beta.mode="separate" and a betas_trans loss term, so the model
#     DOES predict it — and the numbers in section 8 score the model with it on.
#     Rendering with it off shows a different mesh than the one being measured.
#     Pass --no-disable_translation for a like-for-like comparison.
#
#  2. THERE IS NO --output_folder. Outputs land in the CWD, named from the
#     dataset: <dataset><range>_multiview_inference.avi (the grid) and
#     <dataset><range>_singleview_inference_view<N>.mp4 (per view). Every arm
#     produces the SAME filenames, so the arms must run sequentially and be
#     moved aside between runs — an array job would overwrite itself.
#
#  3. Frames come from the dataset, not from a clip you chose. Subclip i starts
#     at i * len(dataset) / K, which is deterministic — so the same
#     --generate_num_subclips / --max_frames give byte-identical frame ranges
#     across arms, which is what makes the panels comparable. Use the same two
#     numbers for every arm, including the reference.
#
# Wrap this in a 1-GPU job (--time=04:00:00 is plenty for 3x300 frames per arm;
# raise --dist_timeout instead if you ever render the full dataset multi-GPU).
# Run from the repo root.

mkdir -p prior_study_results/renders_mv
DS=SMILySTICKS_centred_reprojected_FIXED.h5

  case "$ARM" in
    mv_reference) CKPT="$MV_REF" ;;
    *) CKPT="$RUNS_ROOT/multiview_${ARM}/checkpoints/best_model.pth"
       # same fallback the eval stage applies, so pictures and tables describe
       # the same weights
       [[ -e "$CKPT" ]] || CKPT="$(ls -t "$(dirname "$CKPT")"/checkpoint_epoch_*.pth | head -1)" ;;
  esac
  echo "=== $ARM -> $CKPT ==="
  mkdir -p "prior_study_results/renders_mv/$ARM"

  python -m smal_fitter.neuralSMIL.run_multiview_inference \
      --dataset "$DS" \
      --checkpoint "$CKPT" \
      --smal_file 3D_model_prep/SMILy_STICK_limits_authored.pkl \
      --max_frames 300 --generate_num_subclips 3 \
      --view_indices 0 \
      --no-disable_translation \
      --smoothing_window 0 \
      --export_animation "prior_study_results/renders_mv/$ARM/${ARM}_anim"

  mv "${DS%.h5}"*_multiview_inference.avi \
     "${DS%.h5}"*_singleview_inference*.mp4 \
     "prior_study_results/renders_mv/$ARM/" 2>/dev/null || true
done

#   prior_study_results/sweep/sweep.md   <- HEADLINE, now both modalities
#   prior_study_results/sweep/sweep.csv
#   prior_study_results/lam<L>/comparison/comparison.md
#
# The single-view curve to read the multi-view one against:
#   lambda   axes    viol %   MPJPE mm
#   0        96/162  14.76    1.09      (reference, +0 epochs)
#   1e-4     89/162   2.73    0.97
#   1e-3     85/162   0.26    1.01
#   1e-2     73/162   0.02    1.02
#   1e-1     41/162   0.00    1.05
#   multiview reference: from step 2 — the sweep.md row predating this run
#                        is a leftover and must not be quoted.
#
# WHAT TO EXPECT, and how to read it either way. Multi-view resolves depth
# geometrically, so it has less for a pose prior to fix — a SMALLER multi-view
# delta than the single-view one is a result, not a failure, and it is the
# result the study predicts. What would be informative:
#   * violations fall as steeply as single-view at matched lambda -> the
#     violations were never about depth ambiguity; they are a model-capacity or
#     parameterisation artefact that multi-view does not fix either.
#   * violations fall much less -> the single-view gain really was the prior
#     supplying information the single view lacked. That is the cleaner story.
#   * MPJPE degrades where single-view's did not -> multi-view's fit is tighter
#     against the data, so the same lambda buys less slack. Report the
#     turnover lambda per modality rather than one global recommendation.
#
# CAVEATS to state alongside every number:
#   1. The reference arm received ZERO extra epochs, so reference-vs-lambda
#      mixes the prior with the continuation. Lambda-vs-lambda is clean.
#   2. The multi-view arms got 25 extra epochs, the single-view arms 50. Do not
#      cross-compare deltas between modalities as if they were matched.
#   3. Effective weight scales with authored coverage (79.6 %), so lambda=1e-1
#      is still ~1000x below the old w=100 run. If the whole multi-view curve is
#      flat, the answer is to sweep upward — LAMBDAS="1 10 100" with the same
#      EXTRA_EPOCHS — not to conclude the prior does nothing.
