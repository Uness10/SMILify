# =============================================================================
# 2D-ONLY STUDY — single-view, FROM SCRATCH, no 3D supervision, joint-limit prior
# RWTH CLAIX-2023, account rwth2151 (MaxWall 24 h, MaxSubmit 1000, MaxJobs 800)
#
# The question: with the 3D supervision removed, does the authored joint-limit
# prior buy anything? The earlier lambda sweep could not answer it — those arms
# were 3D-supervised continuations of a 3D-supervised checkpoint, so the prior
# was competing against a keypoint_3d term at weight 20 that already pinned the
# pose. Take that term away and the prior is one of the few things left holding
# the articulation.
#
# Design:
#   - 3 arms, SINGLE-VIEW, all trained FROM SCRATCH for the SAME schedule,
#     each on 2 NODES x 4 H100 = 8 ranks (24 H100 busy across the study)
#       lambda = 0      CONTROL — 2D-only, no prior
#       lambda = 1e-4   low end of the earlier sweep
#       lambda = 1e-1   high end
#   - the training setup is the one that produced sv_reference, byte-for-byte,
#     with exactly two changes: the 3D supervision weights are 0, and the
#     joint-limit weight is the swept lambda
#   - the control is the baseline. sv_reference is NOT a baseline for these arms:
#     it is 3D-supervised, so a delta against it mixes "no 3D" with "prior".
#
# What "no 3D supervision" means here (decided, not guessed):
#   DROPPED  keypoint_3d, global_rot, joint_rot, betas, trans,
#            log_beta_scales, betas_trans
#   KEPT     keypoint_2d, fov, cam_rot, cam_trans, and every regularizer
#            (joint_angle, limb_scale, limb_trans, joint_limit)
#   Dropping only keypoint_3d would have left the model supervised on the exact
#   GT joint rotations and translation — the same 3D information in parameter
#   space. Keeping the camera terms is deliberate: they anchor the projection,
#   and without them the 2D loss is reduced by moving the CAMERA instead of
#   posing the animal.
#
# Run everything from the repo root on $HPCWORK.
# =============================================================================

# so they write MORE than the +50-epoch sweep did, not less. $HOME's quota will
# stop a run mid-epoch with an unhandled OSError inside torch.save.
export RUNS_ROOT="$HPCWORK/smilify_runs"

# -----------------------------------------------------------------------------
# 0a. THE BATCH SIZE — get this before anything else
# -----------------------------------------------------------------------------
# batch_size in the config is PER PROCESS. The trainer hands each rank that many
# samples via DistributedSampler (train_smil_regressor.py:449-461), with one
# optimizer.step() per batch and no gradient accumulation on this path:
#
#     effective batch = batch_size x world_size
#     steps per epoch = (N_train x dataset_fraction) / (world_size x batch_size)
#
# The two move in OPPOSITE directions when the allocation changes. Going from 4
# ranks to 8 with batch_size untouched doubles the effective batch AND HALVES
# the optimizer steps per epoch, so a fixed schedule gets half the gradient
# updates. Nothing compensates: the LR is a pure function of the epoch index
# (train_smil_regressor.py:2079) and is never scaled by world size.
#
# At 8 ranks, to keep sv_reference's regime:  batch_size = <its effective> / 8.
# prepare_2d_only_sweep.sh does that division for you — it wants the EFFECTIVE
# number, so that the answer stays right if the allocation ever changes.
#
# The checkpoint does NOT store world_size, so the training log is the only
# source. A per-rank batch_size read out of the checkpoint's config block is NOT
# the effective batch, and using it as one silently changes the regime:

grep -m1 "Total effective batch size" <sv_ref training log>
grep -m1 "Using distributed samplers for" <sv_ref training log>

export REF_EFFECTIVE_BATCH=<the number from that log>
export WORLD=8            # 2 nodes x 4 GPUs — must match what you submit

# gradient_accumulation_steps is NOT a lever here: the field exists in
# TrainingHyperparameters and the multi-view trainer implements it, but
# train_smil_regressor.py never reads it. Setting it does nothing, silently.


# -----------------------------------------------------------------------------
# 0. ONE-TIME: the code change this study depends on
# -----------------------------------------------------------------------------
# TrainingConfig.get_loss_weights_for_epoch applies the scale/trans mode's loss
# weights LAST, after base_weights and the whole curriculum (training_config.py:534).
# With mode = entangled_with_betas those weights are betas=0.0005,
# log_beta_scales=0.01, betas_trans=0.01 — and until now they came from a
# class-level dict that no JSON config could reach, because
# BaseTrainingConfig.to_legacy_dict() emitted only "mode".
#
# So without the patch, a config that zeroes `betas` in base_weights STILL
# trains with betas=0.0005: the run looks 2D-only in the JSON and is partly
# 3D-supervised on the GPU. Nothing crashes and nothing warns.
#
# The patch makes to_legacy_dict emit the per-mode loss_weights and the trainers
# push them into the legacy dict. The dataclass defaults are value-identical to
# the legacy ones, so it is a no-op for every existing config.
#
# Confirm it is in this checkout before anything else:

grep -n 'loss_weights.*get_mode_loss_weights' smal_fitter/neuralSMIL/configs/base_config.py
grep -n 'SCALE_TRANS_BETA_CONFIG.setdefault' smal_fitter/neuralSMIL/train_smil_regressor.py

# Both must print. prepare_scratch_config.py refuses to write a config if the
# first one is missing, so a forgotten patch cannot silently reach the GPUs.


# -----------------------------------------------------------------------------
# 1. BUILD THE THREE CONFIGS (login node, CPU, ~1 min)
# -----------------------------------------------------------------------------
# One call, three arms, so the only things that can differ between them are
# lambda and the output paths.
#
# num_epochs is NOT typed in: it comes from $SV_BASE_CONFIG, which is what "the
# same training setup" means. It is an ABSOLUTE end epoch and these arms start
# at 0, so the value is the whole schedule.
#

bash scripts/prior_study/prepare_2d_only_sweep.sh

# It prints the arithmetic it used, per arm:
#   batch       : 32 / 8 ranks = 4 per rank (matches sv_reference)
#   [prepare] intended allocation: 8 rank(s) x batch_size 4 = effective batch 32
#
# That intended shape is recorded in each config's _study block, and the
# training sbatch REFUSES an allocation that disagrees — so a forgotten
# --nodes=2 fails loudly instead of quietly running at half the effective batch.
#
# Read what it prints for EVERY arm. The important block is the effective-weight
# table, which is resolved through the REAL loader (curriculum + scale/trans
# override), not read off the JSON:
#
#   [prepare] OK: every dropped term is 0.0 across all <N> epochs
#   [prepare] EFFECTIVE loss weights ...
#     epoch | keypoint_3d | joint_rot | ... | keypoint_2d | joint_limit_regularization
#         0 |           0 |         0 | ... |         0.1 |                      0.0001
#
# Expect two loud notices, both intentional:
#   - SCALE/DEPTH DEGENERACY (see the caveats at the bottom of this file)
#   - "lambda is not comparable across studies"

grep -H '"num_epochs"\|"resume_checkpoint"\|joint_limit_regularization\|checkpoint_dir' \
    configs_runs/singleview_2d_lam*.json

# lambdas distinct, all three checkpoint_dirs distinct.

# -----------------------------------------------------------------------------

# so one submission finishes none of them. Submit ONE link first, read the
# per-epoch time out of its log, then size the chain:
#
#     CHAIN = ceil(num_epochs * epoch_hours / 23)
#
# Leave the hour of slack: the 24 h is wall clock and includes dataset
# construction, the first backbone load and the first checkpoint write.

# Expect, per arm:
#   gpus   : 4 per node x 2 node(s) = 8 rank(s)
#   batch_size 4 per rank x 8 rank(s) -> effective 32
#   allocation        : matches the 8-rank shape this config was built for  OK
#   2 sibling arm(s) agree on the allocation shape  OK

# 4. CHAIN THE REST
# -----------------------------------------------------------------------------
# Each link is an array over all three arms and resumes each arm from the newest
# checkpoint in its own checkpoint_dir. A link that finds its arm already at
# num_epochs exits 0 without allocating anything, so over-provisioning the chain
# is cheap and running short means coming back to submit more.
#
# afterany, not afterok: a job killed at the 24 h wall exits non-zero and that is
# the NORMAL case — it left checkpoints and the next link should pick them up.

CHAIN=8 bash hpc_files/rwth/chain_2d_only.sh

# One arm only (0 = control, 1 = 1e-4, 2 = 1e-1):
#   CHAIN=8 ARRAY=1 bash hpc_files/rwth/chain_2d_only.sh
#
# Back to ONE node per arm (halves the GPUs in flight, and HALVES the effective

# this is refused by the pre-flight unless you also rebuild them:
#   WORLD=4 REF_EFFECTIVE_BATCH=$REF_EFFECTIVE_BATCH \
#     bash scripts/prior_study/prepare_2d_only_sweep.sh
#   CHAIN=12 ARRAY=0-2 SBATCH_EXTRA="--nodes=1" bash hpc_files/rwth/chain_2d_only.sh
#
# Do NOT change the shape partway through: each arm records world_size,
# batch_size and num_epochs into <run_dir>/allocation.json on its first job, and
# every later link refuses to differ from it. Otherwise one arm would train its
# first half at one effective batch and its second at another, at a boundary
# nothing records.

# -----------------------------------------------------------------------------
# 7. READ THE RESULTS — and the caveats that belong next to every number
# -----------------------------------------------------------------------------
#   $RESULTS_2D/sweep/sweep.md                       <- the curve
#   $RESULTS_2D/lam<L>/comparison/comparison.md      <- control vs that lambda
#
# Win condition, same as before: a lambda that lowers the violation rate while
# leaving MPJPE and PCK flat RELATIVE TO THE CONTROL.
#
# CAVEAT 1 — the lambdas are not the earlier study's lambdas. That sweep ran
# against a total loss dominated by keypoint_3d at weight 20. With 3D gone, the
# same numeric lambda is a far larger fraction of the loss, so 1e-1 here is a
# much stronger prior than 1e-1 there. Do not put the two tables side by side.
#
# CAVEAT 2 — best_model.pth is selected on total validation loss, and the limit
# penalty is part of that loss. A constrained arm's "best" epoch is therefore
# chosen under a different objective than the control's. If a delta is small,
# check it also holds at the last checkpoint of each arm, not only at best.
#
# CAVEAT 3 — scale/depth degeneracy, and WHICH ACCURACY NUMBER TO QUOTE.
# mesh_scaling.allow_mesh_scaling is left ON because the study is specified as
# the reference setup MINUS 3D supervision, and TrainingConfig.MESH_SCALING_CONFIG
# says in as many words that the global mesh scale "is trained implicitly via 3D
# keypoint losses". With keypoint_3d and the GT translation both at 0, a
# uniformly larger animal further from the camera reprojects to exactly the same
# pixels, so nothing anchors absolute size; only the limb_scale / limb_trans
# regularizers and the limit prior hold it.
#
# RAW MPJPE IS THEREFORE NOT THE HEADLINE for these arms. It is in mm, so any
# size drift inflates it even when the articulation is perfect. The benchmark now
# reports three numbers instead of one:
#
#   MPJPE (mm)            raw. Includes the size drift. Quote it only alongside
#                         the fitted scale, or not at all.
#   Fitted global scale   predicted size / true size, one number per arm.
#                         1.0 = no drift. THIS IS THE DIAGNOSTIC — read it first.
#   N-MPJPE (mm)          one global scale fitted across the test set, then
#                         measured. Removes a systematic size offset and leaves
#                         every per-frame mistake visible. **This is the headline
#                         accuracy number for this study.**
#   PA-MPJPE (mm)         per-frame rotation+scale+translation alignment. Pure
#                         pose quality, and an OPTIMISTIC bound — it also forgives
#                         per-frame size and orientation error, not just the drift.
#
# How to read them together:
#   scale ~1.0 and N-MPJPE ~ MPJPE     -> no drift; raw MPJPE was fine all along.
#   scale far from 1.0, N-MPJPE << MPJPE -> the size knob drifted, the pose is
#                                         better than raw MPJPE suggested. Report
#                                         N-MPJPE and state the scale.
#   N-MPJPE still large                -> the pose really is worse. A real result.
#   PA-MPJPE << N-MPJPE                -> error is in global placement/orientation
#                                         rather than articulation.
#
# Compare arms on N-MPJPE, never raw MPJPE: the three arms can drift to different
# sizes, and raw MPJPE would rank them by size error rather than by pose. The
# violation-rate columns are unaffected by any of this — joint limits are about
# ANGLES, which do not change when the whole animal is scaled.
#
# sv_reference (3D-supervised) has no drift to correct, so its N-MPJPE and raw
# MPJPE should agree closely. If they do not, suspect the metric, not the model.
#
# If you would rather remove the ambiguity than correct for it, the alternative
# is mesh_scaling.allow_mesh_scaling=false in $SV_BASE_CONFIG, re-run step 1, and
# re-train ALL THREE arms from epoch 0.
#
# CAVEAT 4 — comparing any of this to sv_reference measures "no 3D supervision"
# and "the prior" at once. The control is what separates them, which is why it
# is in the study.
#
# CAVEAT 5 — the arms ran at 8 ranks. If REF_EFFECTIVE_BATCH was set from the
# sv_reference log, the effective batch matches that run and only the number of
# ranks differs (which changes nothing about the optimisation, only the wall
# clock). If it was NOT set, say so: the arms then ran at 8x the base config's
# batch_size and 1/8 the optimizer steps per epoch, and any comparison to
# sv_reference mixes the prior with a different optimisation regime. The three
# arms remain comparable to each other either way — that is what
# allocation.json enforces.
